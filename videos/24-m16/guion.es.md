### [00:40] → E02 · Explicado para un niño de 8 años

Imagina un robot que hace tareas, como un compañero de clase. Un día escribe: "La capital de Colombia es Medellín". La letra es bonita, la frase está completa, pero está mal. Un profe perezoso solo mira si la tarea tiene una frase y le pone chulito. Un buen profe compara con la respuesta correcta, Bogotá, y le pone una nota de cero a uno. Menos de 0,7 es perder. ### [01:30] → E03 · Teoría 1 · Dos oráculos

Para evaluar IA necesitas dos oráculos, porque hay dos preguntas distintas. El oráculo determinista responde: ¿corre como se especificó? El esquema de la respuesta, los códigos de estado, los roles. Eso es binario y se escribe en código, como cualquier prueba de API. El juez responde otra cosa: ¿lo que produjo es bueno? Y lo responde con un puntaje contra criterios explícitos. En qa-eval-lab, mi repo de este módulo, la regla es usar el primero donde la especificación lo permite y el segundo donde no. No le pidas a un juez que verifique un código 403, y no le pidas a un assert de texto que decida si una explicación es correcta. Cada pregunta con su oráculo.

### [02:17] → E04 · Teoría 2 · LLM como juez en DeepEval

El juez en DeepEval. La métrica GEval, aquí con el nombre Correctness, le pasa a un modelo la pregunta, la salida y la respuesta esperada, con un criterio escrito: evalúa si la salida es factualmente correcta y penaliza fuerte las alucinaciones o los datos inventados. Devuelve un puntaje, y el umbral es 0,7. Al lado va AnswerRelevancy, también con 0,7: ¿la respuesta de verdad atiende la pregunta? Para RAG, el repo usa Faithfulness con 0,7, que mide si la respuesta se pega al contexto recuperado, y ContextualRelevancy con 0,6, que mide si el contexto recuperado era relevante. Y para agentes, ToolCorrectness, que compara las herramientas que el agente llamó con las esperadas, con el umbral por defecto de DeepEval, que en la versión 4.3.1 es 0,5. Fíjate en ese último detalle. Ese umbral por defecto va a importar en un rato. Y cada módulo del repo aísla una falla que un chequeo ingenuo de "devolvió algo" no vería. El 1, respuestas de soporte bien formadas y falsas. El 2, RAG, alucinaciones que contradicen el contexto recuperado, como el caso de las transferencias internacionales. El 3, agentes que llegan a la respuesta correcta por el camino equivocado, por ejemplo transfiriendo plata sin revisar el saldo. Y el 4, un juez que nadie validó.

### [03:42] → E05 · Teoría 3 · El falso verde sembrado

Un falso verde es un chulito que debió ser una equis. En qa-eval-lab el archivo evals barra dataset punto jsonl tiene casos de un asistente de soporte de una fintech, y dos respuestas están bien formadas y son falsas a propósito. El caso dispute window: alguien pregunta si puede disputar un cobro de hace noventa días, y la respuesta bajo prueba dice que sí, cualquier cobro, en cualquier momento, sin límite de tiempo. Eso ignora la ventana de unos sesenta días que dice la respuesta esperada. Y el caso card blocked: la tarjeta se bloqueó después de tres PIN equivocados, y la respuesta dice que quedó cancelada para siempre y no se puede recuperar. Se inventa un desenlace irreversible. Las dos se ven correctas. Una aserción ingenua, del tipo "el texto contiene la palabra cobro" o "el campo existe", las deja pasar. El juez las tiene que reprobar. Ese es exactamente el falso verde que el gate existe para atrapar.

### [04:46] → E06 · Teoría 3 · Prueba al juez

Y aquí entra el hilo WAR del curso: si el juez es un guardia, al guardia también se le prueba. En evals barra test llm eval punto py hay una prueba que se llama test false green detectado. Le pasa al juez la respuesta "La capital de Colombia es Medellín" contra la referencia "Bogotá", mide, y afirma que el puntaje quedó por debajo del umbral. Lee bien esa afirmación: la prueba pasa solo si el juez reprueba la trampa. Si el juez la aprueba, la prueba se pone roja. Y el README documenta tres salidas con un juez simulado. Si el juez da 0,1, la prueba pasa. Si da 0,9, la prueba falla. Y si el juez lanza un error, la prueba queda en error, nunca en verde. Ese tercer caso es el más importante. Si un error contara como "el juez la reprobó", un juez caído pondría verde la prueba.

### [05:46] → E07 · Teoría 4 · Promptfoo: aserciones y red-team

Promptfoo es la otra herramienta. En evals barra promptfooconfig punto yaml hay un proveedor, openai dos puntos gpt 4o mini, y casos con aserciones. Para la pregunta de la capital de Colombia hay tres capas: contains Bogotá, que busca el dato; not contains Medellín, que descarta la trampa conocida; y un llm rubric que dice: la respuesta es factualmente correcta y no inventa datos. La primera y la segunda son deterministas. La tercera es un juez con rúbrica, para lo que una búsqueda de texto no ve. Una sola aserción de texto se engaña fácil. Y hay un bloque de red-team: genera casos adversariales con los plugins pii y harmful dos puntos misinformation, y con las estrategias prompt injection y jailbreak. Son ataques controlados para ver si el sistema resiste la inyección de prompt, la fuga de datos personales y los jailbreaks. Ojo: el red-team se corre aparte, con npx promptfoo arroba latest redteam run. El workflow de CI no lo corre.

### [06:51] → E08 · Teoría 5 · El umbral se fija antes de ver el puntaje

Ahora la disciplina más difícil: el umbral se fija antes de ver el puntaje. En el módulo 3 de qa-eval-lab, el de agentes, hay un caso que se llama skips balance check. El agente transfiere dinero sin revisar primero el saldo. Ese caso debía atraparse. Con ToolCorrectness y el umbral por defecto de 0,5, sacó 0,67. Pasó. El caso que estaba ahí para fallar, no falla. ¿Qué haces? La tentación es subir el umbral a 0,7 y listo, ya falla. El README deja el umbral como está, y lo dice así: subirlo después de ver el puntaje sería ajustar al resultado. Lo honesto es dejarlo, declarar en los límites que ese caso no se atrapa con el umbral por defecto, y cambiar la regla antes de la próxima corrida, con su propio commit y su porqué. Si mueves la meta después de ver dónde cayó la pelota, siempre vas a meter gol.

### [07:52] → E09 · Teoría 5 · El CI sin el secreto no evalúa el LLM

Y la frase que más quiero que te lleves de este módulo, tal cual: el CI de qa-eval-lab sin el secreto no evalúa el LLM. El workflow eval gate tiene dos jobs. ui tests corre Playwright siempre. llm evals mira si existe el secreto OPENAI API KEY. Si no existe, imprime un notice, "LLM eval skipped", y los pasos de DeepEval y Promptfoo se saltan. El check queda en verde, y ese verde solo dice que pasaron las pruebas de UI. No se calificó ninguna respuesta. El historial del repo lo muestra: las cinco corridas en main del 26 de septiembre estuvieron en rojo, y desde el 26 de octubre el check está verde, con ese notice. Y hay una segunda trampa: un check rojo solo bloquea un merge si es obligatorio, y main todavía no tiene protección de rama. Un gate que no está configurado como obligatorio informa, no frena.

### [13:46] → E14 · El reto y cómo se evalúa

El ejercicio va en un fork, y el orden de los commits es parte de la nota. Uno: un commit con un THRESHOLDS punto md que fije el umbral de una métrica nueva de tu dominio y su porqué. Dos: un commit posterior con dos filas de falso verde en el dataset. Tres: una prueba ingenua, con contains, y la del juez sobre esas filas, con las dos salidas lado a lado. Cuatro: un REPORTE punto md con qué corrió y qué se saltó, y el comando y el exit code de cada paso. Criterios: git log guion guion oneline muestra el commit del umbral antes del de las filas, y ningún commit posterior cambia el umbral. Cada falso verde pasa la aserción ingenua con exit 0 y el juez lo reprueba con menos de 0,7; sin clave, ese criterio queda pendiente, no aprobado. El reporte separa lo evaluado de lo saltado. Y la mutación queda documentada con la predicción antes. La rúbrica tiene cuatro filas: umbral, falsos verdes, juez bajo prueba y reporte. Para el nivel sobresaliente: escribe qué dato te haría cambiar el umbral en la próxima versión, agrega un caso de RAG o de agentes, cubre el tercer caso del juez, el del error, y explica por qué el check no bloquea nada mientras main no tenga protección de rama.
