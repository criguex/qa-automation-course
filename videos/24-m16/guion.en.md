# Script EN · Module 24 · m16 · Evaluating AI with an LLM judge — DeepEval, Promptfoo, thresholds and false greens

Voice: Cristian Guerra, first person, plain conversational English. Reference pace: 150 words per minute. The `[mm:ss]` marks come from the word count of each block.

### [00:00] → E01 · Hook

You ask an assistant: what's the capital of Colombia? It answers: "The capital of Colombia is Medellín." Status 200. The answer field is there. The sentence is well written. Your test goes green. And the answer is wrong: it's Bogotá. That's a false green, a check that should have come out red. And there's a worse one: the CI check is green, and not a single model answer was evaluated, because the repo didn't have the judge's key. Today you learn to put a judge in place, to prove it's awake, and to read a green check without taking it at its word.

### [00:41] → E02 · Explained like you're 8

Imagine a robot that does homework, like a classmate. One day it writes: "The capital of Colombia is Medellín." The handwriting is neat, the sentence is complete, but it's wrong. A lazy teacher only checks that there's a sentence and gives it a tick. A good teacher compares it with the right answer, Bogotá, and gives it a grade from zero to one. Under 0.7 is a fail. Now here's the trick: we put that Medellín answer there on purpose, as a trap for the teacher. If the teacher dozes off and lets it through, the light turns red. And if the teacher didn't even show up to class, nobody can say the homework passed. All you can say is that nobody graded it.

### [01:31] → E03 · Theory 1 · Two oracles

To evaluate AI you need two oracles, because there are two different questions. The deterministic oracle answers: does it run as specified? The response schema, the status codes, the roles. That's binary, and you write it in code like any API test. The judge answers something else: is what it produced any good? And it answers with a score against explicit criteria. In qa-eval-lab, my repo for this module, the rule is to use the first one wherever the spec allows it and the second one where it doesn't. Don't ask a judge to verify a 403, and don't ask a text assertion to decide whether an explanation is correct. Each question gets its own oracle.

### [02:17] → E04 · Theory 2 · An LLM judge in DeepEval

The judge in DeepEval. The GEval metric, named Correctness here, hands a model the question, the output and the expected answer, along with a written criterion: evaluate whether the output is factually correct, and penalize hallucinations or invented data heavily. It returns a score, and the threshold is 0.7. Next to it sits AnswerRelevancy, also at 0.7: does the answer actually address the question? For RAG, the repo uses Faithfulness at 0.7, which measures whether the answer sticks to the retrieved context, and ContextualRelevancy at 0.6, which measures whether the retrieved context was relevant. And for agents, ToolCorrectness, which compares the tools the agent called with the expected ones, using DeepEval's default threshold, which in version 4.3.1 is 0.5. Keep that last detail in mind. That default threshold is going to matter in a minute. Each module in the repo isolates a failure a naive "it returned something" check would miss. Module 1, support answers that are well formed and false. Module 2, RAG, hallucinations that contradict the retrieved context, like the international wires case. Module 3, agents that reach the right answer the wrong way, for example moving money without checking the balance. And module 4, a judge nobody ever validated.

### [03:38] → E05 · Theory 3 · The planted false green

A false green is a tick that should have been a cross. In qa-eval-lab, the file evals slash dataset dot jsonl holds cases from a fintech support assistant, and two answers are well formed and false on purpose. The dispute-window case: someone asks whether they can dispute a charge from ninety days ago, and the answer under test says yes, any charge, at any time, with no time limit. That ignores the roughly sixty-day window in the expected answer. And the card-blocked case: the card got blocked after three wrong PINs, and the answer says it's permanently cancelled and can't be recovered. It invents an irreversible outcome. Both look right. A naive assertion, something like "the text contains the word charge" or "the field exists," lets them through. The judge has to fail them. That's exactly the false green the gate exists to catch.

### [04:36] → E06 · Theory 3 · Testing the judge

And this is where the course's WAR thread comes in: if the judge is a guard, the guard gets tested too. In evals slash test_llm_eval dot py there's a test called test_false_green_detectado. It hands the judge the answer "The capital of Colombia is Medellín" against the reference "Bogotá," measures it, and asserts the score came in under the threshold. Read that assertion carefully: the test passes only if the judge fails the trap. If the judge passes it, the test goes red. And the README documents three outcomes with a stubbed judge. If the judge returns 0.1, the test passes. If it returns 0.9, the test fails. And if the judge throws an error, the test ends in error, never in green. That third case matters most. If an error counted as "the judge failed it," a crashed judge would turn the test green.

### [05:33] → E07 · Theory 4 · Promptfoo: assertions and red-teaming

Promptfoo is the other tool. In evals slash promptfooconfig dot yaml there's one provider, openai colon gpt-4o-mini, and test cases with assertions. For the capital-of-Colombia question there are three layers: contains Bogotá, which looks for the fact; not-contains Medellín, which rules out the known trap; and an llm-rubric that says: the answer is factually correct and doesn't make anything up. The first two are deterministic. The third is a judge with a rubric, for what a text search can't see. A single text assertion is easy to fool. There's also a red-team block: it generates adversarial cases with the pii and harmful colon misinformation plugins, and the prompt-injection and jailbreak strategies. They're controlled attacks to see whether the system holds up against prompt injection, personal data leaks and jailbreaks. Careful: the red-team runs separately, with npx promptfoo at latest redteam run. The CI workflow doesn't run it.

### [06:32] → E08 · Theory 5 · Set the threshold before you see the score

Now the hardest discipline of all: the threshold is set before you see the score. In qa-eval-lab's module 3, the agents one, there's a case called skips-balance-check. The agent transfers money without checking the balance first. That case was supposed to get caught. With ToolCorrectness and the default threshold of 0.5, it scored 0.67. It passed. The case that was there to fail doesn't fail. What do you do? The temptation is to bump the threshold to 0.7 and call it done, now it fails. The README leaves the threshold where it is, and says it like this: raising it after seeing the score would be tuning to the result. The honest move is to leave it, state in the limits that this case isn't caught at the default threshold, and change the rule before the next run, in its own commit, with its reason. If you move the goal after you see where the ball landed, you'll score every time.

### [07:36] → E09 · Theory 5 · Without the secret, CI doesn't evaluate the LLM

And the sentence I most want you to take from this module, word for word: without the secret, qa-eval-lab's CI doesn't evaluate the LLM. The eval-gate workflow has two jobs. ui-tests always runs Playwright. llm-evals checks whether the OPENAI API KEY secret exists. If it doesn't, it prints a notice, "LLM eval skipped," and the DeepEval and Promptfoo steps are skipped. The check ends up green, and that green only says the UI tests passed. No answer was graded. The repo's history shows it: the five runs on main from September 26 were red, and since October 26 the check has been green, with that notice. And there's a second trap: a red check only blocks a merge if it's required, and main doesn't have branch protection yet. A gate that isn't set up as required just reports. It doesn't stop anything.

### [12:13] → E13 · WAR mutation · Put the judge to sleep

This week's mutation: put the judge to sleep on purpose. In a copy, replace the measurement in test_false_green_detectado with a stubbed judge that always returns 0.9. Before you run it, write down what you expect. My prediction: the test has to go red, because 0.9 isn't less than 0.7. I ran it with pytest and the placeholder key, with an assistant executing under my direction. Result: one failed, an AssertionError. The guard's guard shouted. And to get all three outcomes, I set the stub to 0.1: one passed. And with an empty key, pytest stops while collecting the tests, with the error "OpenAI API key is empty": it ends in error, not in green. That's why CI skips those steps without the secret instead of running them. If your version had stayed green with the judge asleep, the guard wasn't testing anything, and that gets published.

### [13:11] → E14 · The challenge and how it's graded

The exercise lives in a fork, and the order of your commits is part of the grade. One: a commit with a THRESHOLDS dot md that sets the threshold for a new metric from your domain, with its reason. Two: a later commit with two false-green rows in the dataset. Three: a naive test, using contains, and the judge's test on those rows, with both outputs side by side. Four: a REPORTE dot md with what ran and what was skipped, and the command and exit code for each step. Criteria: git log dash dash oneline shows the threshold commit before the rows commit, and no later commit changes the threshold. Each false green passes the naive assertion with exit zero and the judge fails it with a score under 0.7; without a key, that criterion stays pending, not passed. The report separates what was evaluated from what was skipped. And the mutation is documented with the prediction written first. The rubric has four rows: threshold, false greens, the judge under test, and the report. For the outstanding level: write down what data would make you change the threshold in the next version, add a RAG or agent case, cover the judge's third outcome, the error one, and explain why the check blocks nothing while main has no branch protection.

### [15:41] → E16 · Wrap-up

Three ideas. One: an AI answer can be well written and wrong; a shape assertion lets it through, which is why there's a judge, and the judge gets traps planted too. Two: the threshold is written before you see the numbers, in its own commit, and it doesn't move to make a case pass or fail. Three: read the green. Sometimes it only means nobody evaluated anything. Say what ran and what was skipped, with the command and the exit code. In the next module we calibrate the judge for real: checks in code, Cohen's kappa, and human review in the gray zone.
