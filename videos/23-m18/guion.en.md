### [00:39] → E02 · Explained like you're 8

Picture a mail carrier with a big pile of letters at once. Each letter is a test that went wrong. A good mail carrier doesn't stuff them all in the same mailbox. They sort them: this one is a real mistake, this one was bad luck, this one is because the network went down, this one is because the practice data was wrong. And if a letter has no clear address, they don't guess: they hand it to a person. Now another idea. If you changed the car's side mirror, you don't need to check the engine. But if you're not sure what the change touched, you check everything. In this module you'll do both: sort the letters a pipeline hands you, and decide what to check after a change.

### [01:31] → E03 · Theory 1 · Five classes

My rule with the two tools in this module is a single one: deterministic rules decide whatever they can, the model only weighs in on the ambiguous cases, and when in doubt, you do the safe thing. Triage never turns a red green, and the selector never skips a test out of uncertainty. The first tool is jev-ci-triage. It puts every failing test into one of five classes. Regression: the product's behavior changed. Flaky: same code, different outcome. Environment: the network, a dependency, the runner. Test-data: the fixtures or seed data are wrong. And unknown: there isn't enough evidence, so a person looks at it first. The tool doesn't rerun tests, doesn't skip any, and doesn't change the build status. It reads the retries your CI already did and puts a label on each failure, with the evidence behind it.

### [02:27] → E04 · Theory 2 · Rules in order

The rules live in src slash classifier dot ts, and they run in order. Rule one: it failed and then passed on a retry in the same run: flaky. Rule two: there's an infrastructure marker, like ECONNREFUSED, a DNS error, a net colon ERR, a 502, 503 or 504, a crashed browser, and none of the app code this test owns changed: environment. Careful, a plain 500 doesn't count as a marker, because it's often the app's fault. Rule three: with at least minHistory earlier runs, five by default, the outcome flipped two or more times: flaky. Rule four: it passed on every earlier run, it fails every attempt now, the diff touches app code this test owns, it doesn't touch the test or its data, and there are no infrastructure markers: regression. And rule five: anything else is ambiguous and goes to Jev. Look closely at rule two: it needs two things at once. If there's an ECONNREFUSED but the app code also changed, there are two possible explanations, and the rule stays out of it.

### [03:38] → E05 · Theory 3 · Test-data is never decided by a rule

Test-data is never decided by a rule. Telling "the fixture changed" apart from "the product changed" is a question about meaning, and a text pattern can't answer it. That's where Jev comes in, from TypeSafe AI. Jev doesn't generate text. It answers typed questions with probabilities. Each ambiguous failure gets two questions: a choice among the four decidable classes, and a yes-or-no: would this pass if rerun unchanged? The second one is shown to the reader and never decides anything. And there's a threshold: if Jev's confidence is below 0.75, the failure stays unknown and goes to a person, showing which way Jev was leaning. Before anything is sent, src slash redact dot ts strips bearer tokens, key, token and password values, provider-style keys, JWTs, emails, card-like numbers and home-directory paths. The state leaves your machine, redacted, but it does leave. You have to say that out loud.

### [04:37] → E06 · Theory 4 · Confidence moves and the service goes down

Now, what I measured in that repo, and it's the most important part of the module. Confidence moves. For the same input, a new test for a feature the build doesn't have, Jev answered 0.69, 0.71, 0.78 and 0.84. The threshold is 0.75. So on some calls that test would have been labeled flaky, and that's wrong. The chosen class didn't change between calls, but the confidence moved enough to change the routing. Any case near the threshold is unstable. And the service goes down. One afternoon the gateway returned HTTP 429, high demand, on most requests: only 17 of 126 calls succeeded, even with backoff. That's why the tool fails open: the ambiguous failure stays unknown, unverified, with the HTTP error kept in the report, and no guessing. And in the GitHub Action, the fail-on option can make the step fail for certain classes, but never make it pass. The suite's own verdict still stands. And to be fair to Jev, the same log has the good news too: on the clear cases, the ones the rules already decided, Jev agreed with the rules on ten out of ten calls. That's a small sample, and the README says so. Each failure used between 771 and 901 input tokens, and the gateway reported between 0.000032 and 0.000038 dollars per call. Cheap and fast isn't the same thing as stable. You measure all three separately, and you report all three, even when one of them makes the tool look worse.

### [06:17] → E07 · Theory 5 · Test impact selection with a fail-safe

The second tool is jev-test-impact: run only the tests your change can affect. For unit tests, the import graph decides: if you changed a file, the tests that import it, directly or indirectly, run. But black-box tests, the end-to-end ones, don't import the code they exercise. No graph connects src slash views slash layout dot ts to "adding a book updates the header counter." So a "no" from the graph proves nothing, and those tests go to Jev with a yes-or-no question: could this change alter this test's result? The threshold is 0.2, deliberately low, because skipping a broken test costs more than running one too many. On top of that, at-smoke tests always run, and a change to a fullSuiteOn file, like the lockfile or the Playwright config, runs everything. And the fail-safe: any Jev failure runs the full suite. And the full suite still runs on main and every night, so a gap in the selector can delay detection by a few hours, but it can never hide a bug for good.

### [13:07] → E13 · The challenge and how it's graded

The exercise has two parts. One: take ten real failures from your pipeline or your framework, label them by hand into the five classes with their evidence, and write the rules that would have decided the easy ones. Two: in a repo of yours with an impact dot json, based on the demo's, run npx github colon criguex slash jev-test-impact select dash dash base origin slash main across ten commits, and compare, commit by commit, what was selected against what actually failed in the full suite. Criteria: no classification turns a red green. Every failure comes with its evidence: a retry, a marker, history or changed files; anything without evidence stays unknown. Your rule predictions for the demo are committed before running. The impact replay reports three numbers, tests skipped, minutes saved and failures escaped, and it only passes with zero escapes. And there's a fail-safe to the full suite, with the full suite running on main or nightly. The rubric has four rows: classification, rules, impact and mutation. The outstanding level asks for things like a confusion matrix of your rules against your labels, unit tests for your own rules, a comparison against an unsafe policy and a safe one without a model, and adding the test that would have killed the survivor.

### [15:16] → E15 · Wrap-up

Three ideas. One: a red pipeline is a list of questions. Rules decide what they can, the model only weighs in on the ambiguous ones, and whatever has no evidence goes to a person. Two: a model's confidence is a self-report that moves, and the service goes down; so you fail open, and you never turn a red green. Three: in test impact selection the bar is zero escapes, with a fail-safe to the full suite and the full suite on main and every night.
