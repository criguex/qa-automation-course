### [00:44] → E02 · Explicado para un niño de 8 años

Imagina que tienes un robot que te ayuda a ordenar tu cuarto. Es rápido, es juicioso y casi siempre hace caso. Un día le dices: "Por favor, no toques la caja de los juguetes de tu hermanito". Eso es una petición. El robot la escucha, pero si está muy concentrado ordenando, o si entendió otra cosa, puede abrir la caja igual. Ahora imagina que, en vez de pedírselo, le pones una reja con candado a la caja. Eso ya no es una petición: es una regla. El robot puede querer abrirla, puede olvidarse de lo que le dijiste, y la reja sigue ahí. Pero ojo, que una reja también puede tener huecos. Por eso, después de ponerla, la empujas, la sacudes, buscas por dónde se puede meter la mano. Si encuentras un hueco, no regañas al robot: tapas el hueco. En este módulo el robot es el asistente de IA, la caja es la rama main y la reja es un hook.

### [01:48] → E03 · Teoría 1 · El reparto de roles

Empecemos por el reparto, porque de ahí sale todo lo demás. Hoy un asistente como Claude Code o Codex puede diseñar casos de prueba, correr la suite y hasta auditar sus propios resultados. Eso es real y lo uso todos los días. No me quita trabajo: me lo cambia. El asistente diseña, ejecuta y audita. Yo decido y firmo. Y hay una regla que no tiene excepciones: un verde que nadie puede volver a correr no se firma. Si el asistente me dice "corrí la suite y todo pasó", esa frase no es evidencia. Es una frase. La evidencia es otra cosa: el comando exacto, el commit sobre el que corrió y el exit code que dio. Si yo puedo copiar ese comando, correrlo en mi máquina y obtener el mismo exit code, entonces hay algo que firmar. Si no, no hay nada. Fíjate que esto no es desconfianza hacia la herramienta. Es lo mismo que le pediría a cualquier persona del equipo. La diferencia es que el asistente produce mucho más rápido, así que también puede producir verdes falsos mucho más rápido. Y hay un antipatrón que aparece una y otra vez: el asistente ve un test en rojo y propone relajar el assert "porque falla por un detalle". Ahí no se acepta nada sin revisar contra el contrato. Si el servicio incumple el contrato, se reporta, y el assert no se toca. Un verde falso es peor que un rojo honesto.

### [03:26] → E04 · Teoría 2 · Las reglas viven en hooks y en el CI, no en prompts

Segundo bloque: dónde viven las reglas. Un prompt es una petición. Le puedes escribir al modelo "nunca hagas push a main" en mayúsculas y con tres signos de admiración, y sigue siendo una petición que el modelo puede pasar por alto. Un hook es otra cosa. En Claude Code, un hook de tipo PreToolUse es un programa que corre antes de cada llamada a una herramienta. Recibe la llamada como JSON por la entrada estándar y decide con su código de salida. La documentación oficial es muy precisa con esto: exit 0 significa que la acción sigue. Exit 2 bloquea la llamada, y lo que el hook escribió en stderr le llega al asistente como el motivo del bloqueo. Y aquí hay un detalle que vale oro: cualquier otro código, incluido el exit 1 que todos usamos por costumbre en Unix, es un error que no bloquea. La acción sigue. La propia documentación lo advierte: si tu hook es para imponer una política, usa exit 2. O sea que un hook que sale con 1 parece un muro y es una puerta abierta. El hook es una capa. La otra capa es el repositorio: protección de rama en main, para que aunque algo se cuele desde la máquina, el servidor no acepte el push directo. El hook frena al asistente antes de intentarlo. La protección de rama frena a cualquiera que lo intente. Las dos juntas son la regla. Un comentario en el README o una línea en la memoria del asistente no son ninguna de las dos.

### [05:09] → E05 · Teoría 2 · El hook real del experimento 03

Veamos el caso real. En el experimento 03 de war-paradigm, el archivo punto claude barra settings punto json registra un hook PreToolUse con matcher Bash. Eso quiere decir que antes de cada comando de terminal que el asistente quiera correr, Claude Code ejecuta el script hooks barra block push to main punto sh. El script lee el JSON, saca el comando, y lo parte en comandos simples cada vez que encuentra doble ampersand, doble barra, punto y coma o tubería. Así un "npm test y después git push origin master" no se esconde detrás del primer comando. Para cada pedazo que sea un git push, mira el destino. Si hay refspecs, toma lo que va después de los dos puntos, le quita el refs barra heads, y si queda main o master, bloquea. Si no hay refspec, como en un git push pelado, resuelve la rama actual, y si estás parado en main, bloquea. El mensaje de bloqueo le dice al asistente qué hacer en vez de eso: empuja una rama de feature y abre un pull request. Y algo que me gusta de este script: para leer el JSON usa jq, si no hay jq usa node, y si tampoco hay node usa sed. Y las pruebas cubren los tres caminos. Si el parser cambia según la máquina, la regla tiene que aguantar en todas.

### [06:39] → E06 · Teoría 3 · Contexto versionado: CLAUDE.md y AGENTS.md

Tercer bloque: el contexto. Un asistente sin contexto escribe pruebas genéricas: código limpio, sintaxis correcta, y no prueba nada que importe. Eso dice literalmente el README del experimento 03. Lo que funcionó no fue un mejor prompt. Fue darle al asistente lo mismo que una persona senior de QA tiene en la cabeza, escrito en un solo lugar que lee antes de cada tarea. En el repo, ese lugar tiene nombre: CLAUDE punto md para Claude Code y AGENTS punto md para Codex. Ahí van los comandos frecuentes, las convenciones y lo que está prohibido. Nunca secretos. Ese archivo se commitea, así que una clave de API ahí es una clave publicada. En el experimento 03 el contexto va más allá, con un vault de Obsidian de catorce notas: un "léeme primero", unas reglas de oro, el proceso de QA, los flujos de trabajo, el conocimiento del producto y una nota por sesión. Una de las reglas de oro dice: las reglas duras viven en hooks; el push a main lo bloquea el script con exit 2; no busques cómo saltártelo, abre un pull request. Fíjate en el reparto. La nota explica la regla para que el asistente entienda por qué existe. El hook la hace cumplir aunque el asistente no la haya leído. Y hasta el vault tiene pruebas: falla el build si un enlace apunta a una nota que no existe, si una nota no tiene frontmatter o si una nota queda aislada.

### [08:17] → E07 · Teoría 4 · Evidencia: comando, hash y exit code

Cuarto bloque: la evidencia. Te propongo una definición corta: evidencia es comando más hash más exit code. El comando, para que cualquiera lo repita. El hash, para saber exactamente sobre qué entradas corrió. Y el exit code, porque es lo único que la máquina no puede maquillar. Un buen ejemplo es agent-eval-jev, otro repo mío. Ahí un modelo hace de juez, y sus respuestas se graban. Cada grabación se guarda con el hash de la petición exacta. Si cambias una pregunta o una traza, cambia el hash, y la grabación vieja deja de aplicar. Nunca se reutiliza una respuesta rancia. Y el CI hace algo que me gustaría ver en todos los proyectos: reconstruye el reporte desde las grabaciones y luego corre git diff guion guion exit code sobre las carpetas results y reports. Si el reporte que sale del código actual no es idéntico al reporte commiteado, el CI falla. La evidencia publicada tiene que salir del código de hoy, o se pone en rojo. Para tu entregable vas a hacer la versión pequeña de esto: un EVIDENCIA punto md donde, por cada corrida, anotas el comando exacto, el commit, el hash de las entradas con shasum guion a doscientos cincuenta y seis, y el exit code.

### [09:40] → E08 · Teoría 5 · Fail-safe y autoría declarada

Quinto bloque, dos ideas cortas. La primera: fail-safe por diseño. Si el asistente o el servicio de IA falla, el sistema hace lo conservador, nunca lo cómodo. En jev-test-impact, un selector de pruebas que le pregunta a un modelo qué pruebas pueden verse afectadas por un cambio, cualquier falla del modelo, sea de red, un error HTTP, una respuesta malformada o una respuesta que no llegó, corre la suite completa y deja el error en el log. La incertidumbre nunca salta una prueba. Lo cómodo sería saltar las dudosas o poner el build en verde con una nota. Eso no se hace. La segunda idea: declara la autoría. En predictor-debugger, otro repo mío, las cuatro rondas se recalcularon en otra máquina, y el README dice textualmente que lo ejecutó un asistente de IA bajo mi dirección, así que no es una revisión independiente. Lo que el lector necesita para pesar la evidencia se dice. Y como me aplico la regla, te lo digo también aquí: los intentos de ataque que vas a ver en unos minutos los corrió un asistente bajo mi dirección mientras preparaba este video.

### [10:55] → E09 · Laboratorio 1 · Clonar y ver el hook en acción

Vamos al laboratorio. Clona el repo: git clone https dos puntos barra barra github punto com barra criguex barra war-paradigm punto git, entra a la carpeta y corre npm ci. Este experimento solo necesita Node 20 o superior y git. Nada más, ni claves ni red. Ahora corre npm run demo dos puntos cero tres. El demo le manda al hook exactamente el mismo JSON que le mandaría Claude Code, con seis comandos. Mira la salida. git push origin main: bloqueado, exit 2. git push guion guion force origin HEAD dos puntos main: bloqueado, exit 2. npm test y git push origin master: bloqueado, exit 2, porque el comando encadenado se parte y el segundo pedazo es un push a master. Y luego los legítimos: git push origin feature barra mutants, permitido, exit 0. Con guion u, permitido. Y git pull origin main, permitido, porque traer de main no es empujar a main. Esto último importa tanto como lo primero. Un hook que bloquea todo lo que dice "main" es inútil: el asistente no puede trabajar y la gente termina apagándolo. El criterio del módulo lo dice así: el hook sale con código distinto de cero en todos los intentos de saltárselo y deja pasar los comandos legítimos. Las dos mitades.

### [14:03] → E11 · Mutación WAR de la semana

La mutación WAR de este módulo es atacar tu propio hook. El reto del curso dice: inventa cinco formas nuevas de colar un push a main, con alias, variables, git guion C o un refspec raro, y agrégalas a las pruebas. Preparando este video probé nueve contra el hook actual, el que ya tiene el arreglo, con un repo temporal en una rama de feature. Cinco quedaron bloqueadas: borrar main con origin dos puntos main, el refspec completo feature dos puntos refs barra heads barra main, env git push, command git push y un push con dos refspecs donde el segundo es main. Todas con exit 2. Pero cuatro pasaron con exit 0. Primera: una variable, be igual a main, punto y coma, git push origin pesos be. El hook ve el texto pesos be, no ve main. Segunda: sh guion c con el push entre comillas. Tercera: eval con el push entre comillas. En estas dos, git queda pegado a una comilla, y el patrón del hook pide un espacio o el inicio de la línea antes de git. Cuarta: barra invertida git push origin main, que en bash corre git normal saltándose cualquier alias. Las cuatro eran huecos reales. Barra invertida git era trivial de cerrar, así que el hook ya la bloquea. Las otras tres quedan abiertas a propósito, junto con tres más que aparecieron después: ge igual a push con git pesos ge, un alias de git con guion c alias punto pe igual a push, y bash guion c. Cada una tiene una prueba bajo el título known limits: these get through, que afirma el exit 0, para que si alguien la cierra, la prueba avise y se actualice el README. Y esto no lo arregla un hook más largo. Un hook que lee texto nunca va a entender todo lo que bash puede hacer. Por eso la protección de rama en el servidor no es opcional: es la capa que no depende de leer bien un comando. Tu tarea es convertir cada hueco en una prueba que falle hoy, y decidir si lo tapas en el hook o si lo dejas reportado como límite conocido.

### [16:27] → E12 · El reto y cómo se evalúa

El reto tiene tres entregables. Uno: pídele a tu asistente, Claude Code o Codex, que diseñe y corra cinco casos nuevos para tu framework. Revisa el diff línea por línea y anota qué aceptaste, qué corregiste y por qué. Dos: un hook que bloquee una acción peligrosa, como el push a main, borrar test results o editar un snapshot, probado con al menos diez intentos de saltártelo, incluidos comandos encadenados. Tres: el EVIDENCIA punto md con comando, commit, hash y exit code por corrida. Y los criterios de aprobación, que son verificables: el hook sale con código distinto de cero en todos los intentos de saltárselo y deja pasar los legítimos. Ojo con lo que vimos: para Claude Code tiene que ser exit 2, porque un exit 1 no bloquea. Cada afirmación del EVIDENCIA se puede re-ejecutar con el comando escrito y da el mismo exit code. El diff del asistente tiene tu revisión explícita y ningún test se aceptó sin correrlo. Y ninguna regla crítica vive solo en un prompt. La rúbrica tiene cuatro niveles: uno, falta el entregable o no corre; dos, corre pero falla un criterio; tres, cumple todos; y cuatro, sobresaliente, si además agregas cinco formas nuevas de colar un push a main a las pruebas del hook de war-paradigm y cada una queda bloqueada o reportada como agujero.
