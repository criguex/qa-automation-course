### [00:00] → E01 · Hook

git dash c core dot x equals y, push origin main. A push to main with a git option slipped into the middle. The one thing I'd sworn the assistant could never do was slipping through a gap. A mutation found it: someone tried to get past the hook on purpose, and the hook stayed quiet. That's what this module is about: where non-negotiable rules live, and how you prove they hold.

### [00:42] → E02 · Explained like you're 8

Picture a robot that helps you tidy your room. It's fast, it's careful, and it almost always listens. One day you tell it: "Please don't touch your little brother's toy box." That's a request. The robot hears it, but if it's busy tidying, or it misunderstood you, it might open the box anyway. Now picture that instead of asking, you put a fence with a padlock around the box. That's not a request anymore. It's a rule. The robot can want to open it, it can forget what you said, and the fence is still there. But careful: a fence can have holes too. So after you put it up, you push it, you shake it, you look for a spot where a hand could get through. If you find a hole, you don't scold the robot. You patch the hole. In this module, the robot is the AI assistant, the box is the main branch, and the fence is a hook.

### [01:47] → E03 · Theory 1 · Who does what

Let's start with roles, because everything else follows from them. Today an assistant like Claude Code or Codex can design test cases, run the suite and even audit its own results. That's real, and I use it every day. It doesn't take my job away. It changes it. The assistant designs, runs and audits. I decide and I sign off. And there's one rule with no exceptions: a green result nobody can rerun doesn't get signed. If the assistant tells me "I ran the suite and everything passed," that sentence isn't evidence. It's a sentence. Evidence is something else: the exact command, the commit it ran on, and the exit code it returned. If I can copy that command, run it on my machine and get the same exit code, then there's something to sign. If not, there's nothing. This isn't distrust of the tool. It's what I'd ask of anyone on the team. The difference is that an assistant produces much faster, so it can also produce false greens much faster. And there's an anti-pattern that keeps showing up: the assistant sees a red test and suggests loosening the assertion "because it's failing on a detail." Nothing gets accepted there without checking it against the contract. If the service breaks the contract, you report it, and the assertion stays as it is. A false green is worse than an honest red.

### [03:20] → E04 · Theory 2 · Rules live in hooks and CI, not in prompts

Second block: where rules live. A prompt is a request. You can write "never push to main" in capital letters with three exclamation marks, and it's still a request the model can skip. A hook is different. In Claude Code, a PreToolUse hook is a program that runs before every tool call. It gets the call as JSON on standard input and decides with its exit code. The official docs are very precise here. Exit zero means the action goes ahead. Exit two blocks the call, and whatever the hook wrote to stderr reaches the assistant as the reason. And here's a detail worth its weight in gold: any other code, including the exit one we all use out of Unix habit, is a non-blocking error. The action goes ahead. The docs warn about this directly: if your hook enforces a policy, use exit two. So a hook that exits with one looks like a wall and is actually an open door. The hook is one layer. The other layer is the repository itself: branch protection on main, so that even if something slips through on the machine, the server won't accept a direct push. The hook stops the assistant before it tries. Branch protection stops anyone who tries. Together, they're the rule. A comment in the README or a line in the assistant's memory is neither.

### [04:50] → E05 · Theory 2 · The real hook from experiment 03

Let's look at the real thing. In experiment 03 of war-paradigm, the file dot claude slash settings dot json registers a PreToolUse hook with the matcher Bash. That means before every terminal command the assistant wants to run, Claude Code runs the script hooks slash block-push-to-main dot sh. The script reads the JSON, pulls out the command, and splits it into simple commands at every double ampersand, double pipe, semicolon or pipe. That way "run npm test and then git push origin master" can't hide behind the first command. For each piece that's a git push, it looks at the destination. If there are refspecs, it takes what comes after the colon, strips refs slash heads, and if what's left is main or master, it blocks. If there's no refspec, like a bare git push, it resolves the current branch, and if you're on main, it blocks. The block message tells the assistant what to do instead: push a feature branch and open a pull request. And here's something I like about this script: it reads the JSON with jq, falls back to node if jq isn't there, and falls back to sed if node isn't there either. The tests cover all three paths. If the parser changes from machine to machine, the rule has to hold on every one of them.

### [06:19] → E06 · Theory 3 · Versioned context: CLAUDE.md and AGENTS.md

Third block: context. An assistant with no context writes generic tests: clean code, correct syntax, and nothing that matters gets tested. That's literally what the experiment 03 README says. What fixed it wasn't a better prompt. It was giving the assistant what a senior QA person carries in their head, written down in one place it reads before every task. In a repo that place has a name: CLAUDE dot md for Claude Code, AGENTS dot md for Codex. Common commands go there, conventions, and what's off limits. Never secrets. That file gets committed, so an API key in it is a published API key. In experiment 03 the context goes further, with a fourteen-note Obsidian vault: a read-me-first, golden rules, the QA process, workflows, product knowledge, and one note per session. One golden rule says: hard rules live in hooks; a push to main is blocked by the script with exit two; don't look for a way around it, open a pull request. Notice the split. The note explains the rule so the assistant understands why it exists. The hook enforces it even if the assistant never read the note. Even the vault has tests: the build fails if a link points to a note that doesn't exist, if a note has no frontmatter, or if a note is an island.

### [07:48] → E07 · Theory 4 · Evidence: command, hash and exit code

Fourth block: evidence. Here's a short definition: evidence is a command plus a hash plus an exit code. The command, so anyone can repeat it. The hash, so you know exactly which inputs it ran on. And the exit code, because it's the one thing a machine can't dress up. A good example is agent-eval-jev, another of my repos. A model acts as a judge there, and its answers are recorded. Each recording is keyed by the hash of the exact request. Change a question or a trace and the hash changes, so the old recording no longer applies. A stale answer is never reused. And the CI does something I'd love to see in every project: it rebuilds the report from the recordings, then runs git diff dash dash exit-code on the results and reports folders. If the report built from today's code isn't identical to the committed one, CI fails. Published evidence has to come from today's code, or it turns red. For your deliverable you'll build the small version: an EVIDENCIA dot md where, for every run, you write the exact command, the commit, the hash of the inputs with shasum dash a two fifty-six, and the exit code.

### [09:09] → E08 · Theory 5 · Fail safe, and say who did the work

Fifth block, two short ideas. First: fail safe by design. If the assistant or the AI service fails, the system does the conservative thing, never the convenient one. In jev-test-impact, a test selector that asks a model which tests a change could affect, any failure of the model, whether it's the network, an HTTP error, a malformed answer or a missing one, runs the full suite and logs the error. Uncertainty never skips a test. The convenient move would be to skip the doubtful ones, or mark the build green with a note. You don't do that. Second: say who did the work. In predictor-debugger, another of my repos, all four rounds were recomputed on a different machine, and the README says plainly that an AI assistant ran it under my direction, so it isn't an independent review. Whatever readers need to weigh the evidence, you tell them. And since I hold myself to that, I'll say it here too: the attack attempts you'll see in a few minutes were run by an assistant under my direction while I was putting this video together.

### [13:24] → E11 · This week's WAR mutation

This module's WAR mutation is attacking your own hook. The course challenge says: come up with five new ways to sneak a push to main past it, using aliases, variables, git dash capital C or an odd refspec, and add them to the tests. While preparing this video I tried nine against the current hook, the one that already has the fix, using a temporary repo on a feature branch. Five were blocked: deleting main with origin colon main, the full refspec feature colon refs slash heads slash main, env git push, command git push, and a push with two refspecs where the second one is main. All exit two. But four got through with exit zero. One: a variable. B equals main, semicolon, git push origin dollar B. The hook sees the text dollar B, not main. Two: sh dash c with the push in quotes. Three: eval with the push in quotes. In those two, git sits right against a quote mark, and the hook's pattern expects a space or the start of the line before git. Four: backslash git push origin main, which in bash runs plain git and bypasses any alias. All four were real holes. Backslash git was trivial to close, so the hook now blocks it. The other three stay open on purpose, along with three more found later: G equals push with git dollar G, a git alias with dash c alias dot p equals push, and bash dash c. Each one has a test under the title known limits: these get through, which asserts exit zero, so if someone closes one, the test tells you and the README gets updated. A longer hook won't fix this. A hook that reads text will never understand everything bash can do. That's why branch protection on the server isn't optional: it's the layer that doesn't depend on parsing a command correctly. Your job is to turn each hole into a test that fails today, and decide whether you patch it in the hook or leave it reported as a known limit.

### [15:43] → E12 · The challenge and how it's graded

The challenge has three deliverables. One: ask your assistant, Claude Code or Codex, to design and run five new cases for your framework. Review the diff line by line and write down what you accepted, what you corrected, and why. Two: a hook that blocks a dangerous action, like a push to main, deleting test-results or editing a snapshot, tested with at least ten attempts to get around it, chained commands included. Three: the EVIDENCIA dot md with command, commit, hash and exit code for every run. The pass criteria are all checkable. The hook exits non-zero on every bypass attempt and lets legitimate commands through. Remember what we saw: for Claude Code that has to be exit two, because exit one doesn't block. Every claim in EVIDENCIA can be rerun with the command written there and gives the same exit code. The assistant's diff carries your explicit review, and no test was accepted without running it. And no critical rule lives only in a prompt. The rubric has four levels: one, the deliverable is missing or doesn't run; two, it runs but fails a criterion; three, it meets them all; and four, outstanding, if you also add five new ways to sneak a push to main into the war-paradigm hook tests, and each one ends up blocked or reported as a hole.

### [17:12] → E13 · Mini quiz

Three questions. Pause the video after each one. First: you want your assistant to never push to main. Where does that rule live? In the prompt, in a hook that blocks with exit two plus branch protection, in a README comment, or in the assistant's memory? Answer: the hook plus branch protection. A prompt is a request; a hook is a wall, and one you can test. Second: the assistant tells you "I ran the suite and everything passed." What do you sign? ### [18:25] → E14 · Wrap-up

Three things to take with you. One: the assistant designs, runs and audits; you decide and sign, and you only sign what you can rerun. Two: rules that aren't negotiable go in hooks and in CI, with exit two and branch protection, never only in a prompt. And you attack the guard rail the way you attack the product: today you saw four real holes in a hook that already had thirty-three tests; one is closed and the rest are pinned as known limits. Three: evidence is a command, a hash and an exit code, and when something fails, you take the conservative path.
