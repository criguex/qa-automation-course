# Script EN · Module 22 · m21 · Mutants that learn — the ledger, prioritization, and mutants that measure the auditor

Voice: Cristian Guerra, first person, plain conversational English. Reference pace: 150 words per minute. The `[mm:ss]` marks come from the word count of each block.

### [00:00] → E01 · Hook

I made a mutant fail on purpose. The ledger wrote it down: failures, one. The engine's promise is clear: on the next run, that mutant goes first. I ran it again. The first one to run was the usual one, and the ledger was back to zero, as if nothing had happened. The loop that learns didn't remember a thing. And no test had noticed, because nobody had asked the memory the same question we ask the product: does it actually work? I found it while preparing this video, and it's fixed now. Today it's mutants that learn, and how you prove they really do.

### [00:42] → E02 · Explained like you're 8

Think about a soccer goalkeeper. In the last match, every goal went in on the left. A good coach doesn't start practice by shooting at random. They shoot to the left first, where the keeper failed. Then they try new spots the keeper hasn't faced yet. And last, the right side, where the keeper always makes the save. To do that, the coach keeps a notebook of what happened in every match. But notice something: the order of the shots changes, and a goal is still a goal. Shooting left first doesn't make a goal count for less. And if someone throws the notebook away after every match, the coach starts from scratch every single time. In this module, the shots are mutants, the notebook is the ledger, and practice is the next run.

### [01:36] → E03 · Theory 1 · From a snapshot to a movie

Running mutants once is a snapshot. Saving what happened and using it on the next run is a movie. That's what civica-playwright-challenge sets out to do. It's a Playwright and TypeScript framework that tests two IMDb flows against a deterministic mock layer. Its mutant engine takes a golden flow, search for a title and open it, and expands it into three classes. Equivalent: the input changes but the result must not, like INCEPTION in capitals. Boundary: an edge that should still work, like a prefix of the title. Negative: the result must change, like a nonsense word that should find nothing. Then comes the learning part: a function called prioritize that orders the mutants like this. First, the ones that failed before, because that's the fastest feedback on known weak spots. Next, the ones never seen, because that's new coverage. And last, the ones that always pass. Three seeds and seven mutators give you twenty-one mutants.

### [02:38] → E04 · Theory 2 · The ledger is a reporter

Where does that memory live? In a Playwright reporter. The file reporters slash mutationInsightsReporter dot ts listens for every test that finishes. If its title carries the at-mutant tag, it saves the status and the duration. At the end of the run it opens the ledger, ledger slash mutation-insights dot json, and for each mutant it keeps the latest status plus four more things. Runs, which counts every run, ever. History, with the statuses of the last five. Failures, which counts only the failures inside those five. And timeouts, kept apart. That five is called HISTORY WINDOW, and it's how the ledger forgets: a mutant that failed once goes back to its place after five runs. Timeouts don't move it up, because a timeout usually says more about the machine than about the mutant. Notice the folder: ledger, not test-results. Playwright empties test-results at the start of every run. Until recently the ledger lived there, and in this week's mutation you'll see what that did. The ledger folder is in the gitignore: on a fresh clone it's empty and the mutants run in declared order. In CI, the workflow downloads the mutation-insights artifact from the latest completed run on main before the mutants, and uploads the new one at the end, kept for ninety days. One more detail about the reporter: the mutant id is the first word of the test title, so if someone renames a mutant, the ledger treats it as brand new, never seen, and its history is gone. That's not a bug, it's a design decision, but you need to know it before you trust the order.

### [04:26] → E05 · Theory 3 · Reordering can't change a verdict

Third idea, and it's a design rule: reordering must not break determinism. It changes the order, never any mutant's verdict. It doesn't add or drop mutants either, and it never retries anything. The prioritize function does a stable sort: within each weight, mutants keep the order they were declared in. So with the same ledger, the order is always the same. Now think about what the opposite would mean. If a mutant passes when it runs third and fails when it runs first, the problem isn't the mutant: there's state shared between tests. That's a bug in the harness, and you fix it in the harness. That's why one of the module's criteria is that every mutant's verdict is the same in any order. If that ever stops being true, the ledger just found you a problem more serious than any mutant.

### [05:23] → E06 · Theory 4 · Mutants that measure the auditor

Now the same idea aimed at a different guard. Civica has a security auditor with three proofs of concept: it scans a web flow's traffic for exposed personal data and secrets, missing security headers and cookies without their flags, and it analyzes an Android manifest for dangerous permissions. How do you know that auditor catches what it says it catches? With mutants. You start from a hardened baseline, a secure web response and a hardened Android manifest, and plant exactly one defect per mutant. An unmasked card number in the body. The Content Security Policy header stripped. Strict Transport Security stripped. X-Content-Type-Options stripped. A cookie without Secure, HttpOnly or SameSite. And the READ SMS permission added to the manifest. Each mutant runs the real scanner and asks: did you catch your own defect? If it doesn't, the auditor has a blind spot. There's a seventh one in the catalog, stripping X-Frame-Options, marked as equivalent; you'll see why in the lab. And this is where the baseline idea from earlier modules comes back. Before you plant defects, the baseline has to be genuinely clean. Civica's POC 1 checks that: on the vulnerable flow of a fictitious account, the auditor reports sixteen findings, three critical, three high, eight medium and two low. On the secure response and its cookie, zero. That zero is the false-positive control. If the baseline already produced findings, a "detected" mutant would tell you nothing, because the auditor would shout with or without the planted defect.

### [07:02] → E07 · Theory 5 · Metamorphic relations

Last theory block. On civica's roadmap, the next step is metamorphic relations. A metamorphic relation is a rule between related inputs and their outputs. It's useful when you don't know the exact answer, but you do know how two answers should relate. That's the idea underneath the equivalent class: you don't know the exact list that should come back, but you know what must not change. The roadmap's example, in MUTATION-TESTING dot md, now says: with the mock's case-insensitive substring search, results for a prefix of X contain the results for X. Search for "The": four movies come back, because "The" shows up in The Shawshank Redemption, The Godfather, The Dark Knight and The Lord of the Rings. Search for "The Dark Knight": one comes back. The prefix returns more, not less. And here's a catch, because the roadmap didn't always say that. It used to say the opposite: that results for X were a superset of results for a prefix of X. Written that way, the relation would have failed against correct code. We caught it while preparing this video, by checking it against the spec, and it was fixed in the same commit that fixed the ledger. The rule stands: before you implement a relation, check it against what the system actually does. The classic reference is the paper by Chen and colleagues on metamorphic testing, in ACM Computing Surveys, 2018.

### [09:46] → E09 · Lab 2 · Running the auditor

Run npm run test colon audit dash dash securityMutants. Seven tests, seven passed: six mutants and one test for the equivalent. The log says: Security mutant kill rate six out of six, one hundred percent, one equivalent excluded. In test-results slash audit slash security-mutants dot json each mutant shows up as Killed, with the evidence "detected by the auditor," and the equivalent one is listed separately, with its reason. Its ledger lives in ledger slash audit-mutation-insights dot json, apart from the other one so the two loops never collide, and for now it's only recorded: nothing reorders the security mutants yet. Now, what are you claiming with that six out of six? That the auditor detected the six observable defects planted in the catalog. Nothing more. Whatever isn't in the catalog isn't measured. A kill rate talks about the catalog that exists, not about every possible defect. That's why the next step is adding a mutant of your own.

### [10:50] → E10 · Lab 3 · The mutant that plants nothing

The course used to suggest stripping X-Frame-Options. I added it while preparing this video, on a copy, as one more line in the list of headers in src slash audit slash securityMutations dot ts. I ran it: one failed, six passed, and the report said kill rate six out of seven, 86 percent. It survived. And the module's rule is clear: if a new mutant survives, you report it, and you don't adjust the mutant to make it die. Fine. But before you write "the auditor doesn't detect a missing X-Frame-Options," look at the baseline. The secure headers are four: content type, a Content Security Policy with frame-ancestors none, Strict Transport Security and X-Content-Type-Options. X-Frame-Options was never there. Stripping it planted nothing. And the clickjacking protection is still in place, because the auditor accepts frame-ancestors in the CSP or X-Frame-Options, either one. It's an equivalent mutant in the classic sense: it doesn't change behavior, and no test can kill it. The finding was real, but it was about the catalog, not about the auditor. And that's how it ended up in civica: the mutant is in the catalog, marked as equivalent, with its reason, and left out of the kill rate. That's why it now says six out of six, one equivalent excluded. And it doesn't stay a promise: a test tagged at-auditEquivalent checks on every run that the auditor's findings on the mutated headers are identical to the baseline's. If the baseline ever changes so that stripping that header becomes visible, that test fails and the mutant has to be reclassified.

### [12:35] → E11 · WAR mutation · Did the ledger remember?

This module's mutation says: force a mutant to fail and check that the next run puts it first. I did it while preparing this video, on the code from before the fix, with an assistant running the commands under my direction, on Playwright 1.63. I changed the gibberish mutator so it searched for the real title, so all three gibberish mutants failed. The ledger ended up with status failed, runs one, failures one. Perfect. Then I undid the change and ran again, on a single worker so the order would be easy to see. The first one to run was inception exact, not gibberish. And the ledger said runs one, failures zero again. Before that I'd run the suite twice in a row, and runs never got past one. What was going on? The ledger lived inside test-results, and that's Playwright's output folder, which gets emptied at the start of every run. By the time the reporter went to add things up, the old file was gone. Dash dash list did show the reordering, because listing doesn't empty the folder. In other words: the loop learned within a run and forgot everything when the next one started. You couldn't see it by reading the code. You saw it by running twice and looking at runs.

### [14:01] → E12 · WAR mutation · The fix and its evidence

The fix landed in civica in commit b240008, and it's five changes. One: the ledger moved to the ledger folder, outside test-results; if it finds an old one in test-results, it reads it once and carries it over. Two: forgetting. Failures used to be cumulative, and a mutant that failed once stayed first forever. Now it only counts the last five runs. Three: timeouts get their own counter and don't move a mutant up; before, a timeout counted the same as a real failure. Four: a corrupt ledger doesn't stay quiet anymore. loadInsights used to return an empty ledger without a word. Now the run prints a warning with the alert sign, adds a ledger-warning annotation to the HTML report, runs in declared order, and keeps the broken file as dot corrupt before writing a fresh one. I checked by writing garbage into the file: the warning showed up. And five: CI downloads the ledger from the latest completed run on main and uploads it again at the end, kept for ninety days. On the first run after the fix there was no artifact, so it started fresh, without an error. On the next one, the log says it restored the ledgers from the previous run, and the artifact came out with runs two for all twenty-one mutants. All of that is covered by seven unit tests in a unit project: ordering, forgetting, timeouts, migrating the old file, the corrupt file and the missing one.

### [15:39] → E13 · The challenge and how it's graded

The challenge. One: in civica, run the mutation suite twice and show that the ledger remembers: runs goes from one to two. Two: force a mutant to fail and show in the log that the next run puts it first. Three: add a new security mutant, for example stripping just the frame-ancestors directive from the CSP, the equivalent mutant's twin, or slipping a JWT into the body, and write down beforehand whether you think it dies. The deliverable is the two-run ledger, the evidence of prioritization, and the security mutant with its prediction and verdict. Criteria: the second run's log shows the mutant that failed in the first run going first. The ledger shows each mutant's runs, history, failures and timeouts, and between your two runs, runs goes from one to two. If your security mutant survives, it's reported as a finding and the mutant was left alone; and I'll add: with an explanation of whether it actually planted a defect. And every mutant's verdict is the same in any order. If you want to go further, give the ledger its own WAR mutation: write garbage into the file and check that the run warns you instead of staying quiet. Four-level rubric: missing, runs but fails a criterion, meets everything, and outstanding if you also implement the roadmap's metamorphic relation: results for a prefix of X contain the results for X.

### [18:14] → E15 · Wrap-up

Three ideas. One: a ledger turns a snapshot into a movie, but memory gets tested too. Today you saw a loop that reordered correctly and forgot everything between runs, and the only way to see it was to force a failure and watch the next run. It's fixed now, and on top of that it forgets on purpose and warns you when it breaks. Two: reordering changes the order, never the verdict. If the order changes a verdict, the bug is in the harness. Three: a surviving mutant gets reported without touching it, and before you blame the auditor, make sure the mutant actually planted something.
