# Script EN · Module 21 · m29 · Running mutants — generate, run, classify, and learn from every run

Voice: Cristian Guerra, first person, plain conversational English. Reference pace: 150 words per minute. The `[mm:ss]` marks come from the word count of each block.

### [00:00] → E01 · Hook

A mutant expects the server to say 403: forbidden. The server says 500. Something crashed. Did the mutant die? A lot of people would say yes: the test failed, the change didn't get through, KILLED. And with that call, your kill rate goes up, and it's a lie. A 500 tells you something broke, not that the rule rejected the change. If the server were down all day tomorrow, you'd post the best kill rate of your career. Writing a mutant is easy. Running it without lying to yourself is the hard part. That's what this module is about.

### [00:40] → E02 · Explained like you're 8

Imagine you hide six broken toys in a box and ask the guard to find them. If they find five, their score is five out of six. Easy. Now imagine that halfway through, the lights go out. The guard doesn't find the sixth toy, but not because they're a bad guard. They just couldn't see. That attempt doesn't count for or against them. You write it down in a separate column and try again when the lights come back. And if the guard couldn't even get into the room because the door was locked, that doesn't count either: the game never started. In this module you'll learn to keep those columns apart.

### [01:24] → E03 · Theory 1 · The full cycle

The cycle has six steps. Generate: write mutants as data. Run: the baseline first, then a single change. Classify: give each result one of five states. Score: work out the kill rate. Record: save what happened in a ledger. Prioritize: use that ledger to order the next run. We'll walk through all six with two repos. For the first five, war-paradigm, experiment 02: a small document app with a golden flow and seven mutants. For the last one, civica-playwright-challenge: a Playwright framework with a mutant engine that learns between runs. You'll need Node 20 or later, plus what you already know about Playwright with TypeScript and API testing.

### [02:08] → E04 · Theory 2 · Generating without scripts

Generate. In war-paradigm, tests slash scenarios dot ts holds seven objects. Each one makes a single change to the golden flow and declares the rejection the app must give. role-swap, a viewer approves: 403. drop-input, the owner is dropped on create: 422. reorder, publish without approving: 409. stale-token, an expired token: 401. boundary, a title that's too long: 422. self-grant, the editor makes themself admin: 403. And viewer-create, a viewer creates a draft: 403. Civica generates differently. A function, generateSearchMutants, takes a seed title, say Inception, and expands it into seven mutants in three classes. Equivalent: the result must not change, like INCEPTION in capitals, inception in lowercase, or the title padded with spaces. Boundary: an edge that should still work, like a partial prefix. Negative: the result must change, like the title with a junk suffix, or pure gibberish. Three seeds times seven mutators: twenty-one mutants.

### [03:06] → E05 · Theory 2 · Careful with the word "equivalent"

A warning about one word, because it will trip you up in an interview. In classic mutation testing, with Stryker or PIT, an equivalent mutant is one no test can kill, because it doesn't change the program's behavior. It's a false survivor. In civica, equivalent means something else: a variation of the input, like INCEPTION or inception, that must give the same result as the original. That's closer to a metamorphic relation than to an equivalent mutant. Same name, different idea. When you read a report, always ask which one it means.

### [03:43] → E06 · Theory 3 · Running in order

Run. The file tests slash scenario-runner dot ts does things in a fixed order. First it validates the mutant's contract: it needs an id and a name, the expected rejection has to be a 4xx, and the step to mutate has to appear exactly once. Then it resets the state and expects a 204. Then, step by step, it logs in with the right role and runs the unmutated steps as a baseline, expecting the happy-path codes: 201 on create, 200 on approve and publish. Only when all of that has gone right does it mutate exactly one step. If anything before that fails, the mutant tells you nothing about the suite. And notice: the runner doesn't hide it. It classifies it and leaves it in the report, just outside the score.

### [04:36] → E07 · Theory 3 · Five states

Classify. The Outcome type in tests slash scenario-evidence dot ts has five states. KILLED: the mutation gets exactly the expected 4xx. SURVIVED: the mutation gets a 2xx; the app accepted something it should have rejected. INCONCLUSIVE: it gets a 5xx, or a rejection other than the expected one. If you expected 403 and got 422, something rejected it, but not the rule you were testing. INVALID BASELINE: a precondition failed, like login or reset returning something that isn't a 5xx. And INFRA ERROR: the request or the runner failed, or the test ended without attaching evidence. That's what noEvidence is for: if a test was interrupted or skipped before recording its result, it comes out as INFRA ERROR, never as a survivor. Look at classifyMutation, it's four lines. If the code is 500 or above, INCONCLUSIVE. If it's between 200 and 299, SURVIVED. If it equals the expected code and it's a 4xx, KILLED. Anything else, INCONCLUSIVE. That order matters: the first question it asks is whether the server fell over.

### [05:44] → E08 · Theory 4 · Scoring, known survivors and strict mode

Score. Kill rate is KILLED over KILLED plus SURVIVED. The other three states show up in the report and stay out. The scoreboard line says it like this: five of seven scored mutants killed, two survived, zero excluded from score. Put the excluded ones in the denominator and a crashed server drags your kill rate down. Count them as KILLED and it goes up. Both are false. Now, the known survivors. self-grant carries a known field describing the finding, and so does viewer-create, a hole I found while preparing this course: the app lets a viewer create drafts. In the default run each one comes out as KNOWN SURVIVOR, printed in red, and the run stays green, because Playwright marks it as an expected failure. But that marker is only applied after an accepted mutation has actually been observed. A broken reset can't pass itself off as a known survivor. With MUTANT LAB STRICT set to one, which is npm run test colon strict, each of those survivors fails the run. And when someone fixes the bug, the scoreboard shows it as FIXED.

### [06:58] → E09 · Theory 5 · Evidence, and the oracle's limit

The evidence lands in test-results slash mutant-evidence dot json. Per scenario: expected and observed status, phase, reason, the git revision, and SHA-256 hashes for seven inputs: the app, the flow, the scenarios, the runner, the classifier, the spec and the lockfile. And random seed set to null, because the run uses no randomness. With that, someone else can reproduce your kill rate by hand. Now the limit, which the README states plainly: the oracle works at the HTTP level, plus a role read-back for self-grant. A matching status code doesn't prove semantic equivalence. That's why the runner never emits an EQUIVALENT state or claims global invariants. If the app answered 403 but still changed something underneath, this oracle wouldn't see it. Knowing how far your instrument reaches is part of measuring.

### [07:50] → E10 · Lab 1 · Run it, read it, do the math by hand

To the lab. Clone war-paradigm, npm ci, and npx playwright install dash dash with-deps chromium. Run npm run demo colon zero two. You'll see the scoreboard: five KILLED, two KNOWN SURVIVORS, five out of seven. Open the evidence JSON and write down, for each scenario, expected status, observed status, outcome and phase. Work out the kill rate by hand. Now run npm run test colon strict dash w experiments slash zero two mutants. I ran it while preparing this video: two failed, five passed, and npm exits with code one. Write down when you'd use each mode. My answer: the default for everyday work, so the known finding stays visible without blocking the whole team, and strict mode for a release gate. Then run npm run test colon unit dash w experiments slash zero two mutants. That's five classifier tests, and all five pass. Read them and add a sixth: if 403 was expected and 404 comes back, the result has to be INCONCLUSIVE.

### [08:56] → E11 · Lab 2 · Two mutants with predictions, and "Kill it yourself"

Now add two mutants to scenarios dot ts. The course suggests two. viewer-publish: on the publish step a viewer acts, 403 expected. And a two-character title on create, with 422. The golden rule: commit your prediction before you run. Get it into git, with a date, what you think will happen to each one. Then run it and see if you were right. If you were wrong, that's information too: your mental model of the app doesn't match the app. And finally, "Kill it yourself." In app slash server dot js, change editMember so only an admin can change roles. Run the demo again. I did it on a copy: the scoreboard says FIXED self-grant, six of seven killed, and strict mode still exits with one, because viewer-create is still open. Once the finding is closed, you remove the known field.

### [09:52] → E12 · Lab 3 · Civica's learning ledger

Now civica. Clone the repo and run npm ci; Playwright installs Chromium on its own in the postinstall. Without running anything, look at the order: npx playwright test dash dash project equals mutation dash dash list. Twenty-one tests, and within each seed the declared order: exact, upper, lower, padded, prefix, garbage-suffix, gibberish. The order comes from prioritize, in src slash support slash mutationInsights dot ts. It gives weight zero to mutants that failed in their last five runs, weight one to ones never seen, and weight two to the rest, with a stable order within each weight. It changes the order, never the verdict. The memory lives in ledger slash mutation-insights dot json: for each mutant it keeps runs, which counts every run, history, with the statuses of the last five, and failures and timeouts, counted inside those five. Try it: run npm run test colon mutation twice and look at runs: one, two. Find inception dash dash gibberish, the last one in its seed, change the last status in its history to failed and set failures to one. List again. I did: inception gibberish jumps to first place in the Inception seed. Now the forgetting: run it five more times and list after each one. It stays first until that failed slides out of the five-run window, and after the fifth run it's back in its place.

### [11:23] → E13 · Lab 3 · What that ledger didn't do

This block is a WAR story. When I was preparing this video, civica's ledger had five limits. Four were right there in the code. Failures was cumulative, so a mutant that failed once stayed first forever. The reporter counted a timeout as a failure, without separating infrastructure the way war-paradigm does. If the JSON was corrupt, loadInsights quietly returned an empty ledger. And in CI the ledger was uploaded as an artifact, but nothing downloaded the previous one. I found the fifth by running things, with an assistant under my direction, on Playwright 1.63: the ledger lived inside test-results, the output folder Playwright empties at the start of every run. I ran it twice and runs was still one. The loop remembered nothing between runs. All of that was fixed in commit b240008. The ledger moved to the ledger folder. It forgets through a five-run window, HISTORY WINDOW. Timeouts get their own counter and don't move a mutant up. A corrupt ledger prints a warning with the alert sign, adds a ledger-warning annotation to the report, runs in declared order and keeps the broken file as dot corrupt. And CI downloads the ledger from the latest completed run on main and uploads it again, kept for ninety days. Your job is no longer to confirm the bug, but to test the fix: break the ledger on purpose, write garbage into it, and check that the run warns you instead of staying quiet. I did: the warning showed up and the dot corrupt file was there.

### [13:05] → E14 · Lab 4 · Mutants that measure the auditor

Last lab. Civica also has mutants that measure a security auditor. On a hardened baseline, a secure web response and a hardened Android manifest, one defect is planted per mutant: an unmasked card number in the body, the CSP header stripped, HSTS stripped, X-Content-Type-Options stripped, a cookie without Secure, HttpOnly or SameSite, and the READ SMS permission added to the manifest. Each mutant runs the real scanner and asks whether it caught its own defect. Run npm run test colon audit dash dash securityMutants. Seven passed: six mutants and one test for a seventh, stripping X-Frame-Options, which is a true equivalent in the Stryker and PIT sense. The baseline never sends that header, because its CSP already carries frame-ancestors none, so stripping it plants nothing. That's why the log says: kill rate six out of six, one hundred percent, one equivalent excluded. And that test checks on every run that the equivalent really changes nothing. Its ledger lives separately, in ledger slash audit-mutation-insights dot json, and for now it's only recorded. Add a mutant of your own in src slash audit slash securityMutations dot ts, for example stripping just the frame-ancestors directive from the CSP, and write down beforehand whether you think it dies. If it survives, that's a finding about the auditor: don't touch the mutant to make it die. In the next module you'll see how we found out that X-Frame-Options planted nothing.

### [14:39] → E15 · This week's WAR mutation

This week's mutation is cheating on purpose to see if the harness catches you. In scenario-evidence dot ts, change the first line of classifyMutation so a 5xx counts as KILLED. Before you run anything, write down which test should fail. I bet on the second one: accepted mutation survives, but server errors are inconclusive, because that's the one asking about a 500. Run npm run test colon unit dash w experiments slash zero two mutants. Result: four pass, one fails, that exact one, with the message: expected INCONCLUSIVE, got KILLED. And npm exits with code one. The harness has teeth against that cheat. If no test had failed in your version, you'd have a blind spot, and the next step would be writing the test that closes it. When you're done, revert the change.

### [15:33] → E16 · The challenge and how it's graded

The deliverable: a fork of war-paradigm with the two new mutants, the unit test and the fix; the mutant-evidence dot json from before and after; civica's ledger with runs going from one to two, evidence of the reordering and the forgetting, and the output of the broken ledger; and a new security mutant with its verdict. Criteria: your kill rate uses only KILLED and SURVIVED, and you can reproduce it by hand from the JSON. The two new mutants have their prediction in a commit that comes before the run. The new unit test passes. After "Kill it yourself," self-grant comes out FIXED and strict mode fails only on viewer-create. And the dash dash list output before and after editing the ledger shows the order changing, the mutant goes back to its place after the fifth run, the broken ledger produces the warning and the dot corrupt file, and every mutant's verdict stays the same. The rubric has four rows. Classification: from counting any failure as KILLED, up to having your own unit test that catches a badly written rule. Mutants as data: from loose scripts, up to one change per mutant with a committed prediction and a new edge case. Survivors: from deleting them, up to fixing them with before-and-after evidence. Ledger and order: from no ledger at all, or one that gets wiped between runs, up to testing its edges: forgetting after five runs, a timeout that doesn't move the mutant up, and a broken ledger that warns you.

### [17:13] → E17 · Mini quiz

Three questions, with a pause. First: a mutant expected 403 and the server answered 500. How is it classified? Answer: INCONCLUSIVE. A 5xx doesn't prove the rule works, and it stays out of the score. Second: you run six mutants, four KILLED, one SURVIVED and one INFRA ERROR. What's the kill rate? Answer: four out of five, 80 percent. The INFRA ERROR is shown, but it's in neither the top nor the bottom of the fraction. Third: a mutant's test ends without attaching evidence. How is it classified? Answer: INFRA ERROR, outside the score. No evidence, no verdict about the suite.

### [18:09] → E18 · Wrap-up

Three ideas. One: five states, not two. KILLED and SURVIVED tell you about your suite; INCONCLUSIVE, INVALID BASELINE and INFRA ERROR tell you about your experiment, and they're shown but not counted. Two: your kill rate has to come out of the JSON by hand, and your predictions have to be in git before you run. Three: a ledger that reorders is only useful if it actually remembers, and you test that too: that's how we saw civica's didn't, and that's how you check today that it does.
